# 서비스 수준 목표

서비스 수준 목표(SLO)와 서비스 수준 협약(SLA)은 대규모 언어 모델(LLM) 배포 환경의 품질과 신뢰성을 보장하는 데 중요합니다. 사용자 기대와 비즈니스 요구 사항을 충족하기 위해 시스템이 달성해야 할 성능 및 신뢰성 목표를 측정 가능한 형태로 정의합니다. 아래에서는 다양한 LLM 활용 사례에 대한 SLO/SLA의 핵심 개념, 상충 관계 및 예제를 설명합니다.

## 정의

### 서비스 수준 목표(SLO)

SLO는 시스템 운영과 최적화의 기준이 되는 내부 성능 및 신뢰성 목표입니다. 일반적으로 지연 시간, 처리량, 오류율처럼 측정 가능한 지표로 정의하며, 시스템 성능을 평가하는 기준으로 사용합니다.

### 서비스 수준 협약(SLA)

SLA는 서비스 제공자와 사용자 또는 고객 간에 맺는 공식적인 협약입니다. 서비스 제공자가 약속하는 성능과 신뢰성 보장 수준을 명시합니다. 합의한 목표를 달성하지 못했을 때의 위약금이나 보상도 포함하는 경우가 많습니다.

## 지연 시간과 처리량의 상충 관계

LLM 배포 환경의 SLO와 SLA를 설정할 때는 지연 시간, 처리량 및 비용 효율성 사이에서 균형을 맞춰야 합니다:

- **지연 시간**: 개별 요청을 처리하는 데 걸리는 시간으로, 첫 토큰 생성까지 걸리는 시간(TTFT)과 토큰 간 지연 시간(ITL) 등이 포함됩니다. 응답성이 중요한 사용자 대상 애플리케이션에서는 낮은 지연 시간이 필수적입니다.
- **처리량**: 초당 처리하는 요청 수입니다. 대규모 워크로드를 효율적으로 처리하려면 높은 처리량이 필요합니다.
- **비용 효율성**: 요청당 비용으로, 시스템의 리소스 사용률과 처리량에 따라 달라집니다. 비용 효율성을 높이려면 처리량을 늘려야 하는 경우가 많으며, 그 결과 개별 요청의 지연 시간이 늘어날 수 있습니다.

예를 들어, 채팅 애플리케이션은 원활한 사용자 경험을 위해 낮은 지연 시간을 우선할 수 있고, 콘텐츠 생성용 배치 처리 시스템은 비용을 줄이기 위해 높은 처리량을 우선할 수 있습니다.

## 일반적인 LLM 활용 사례의 SLO/SLA 예제

### 외부 애플리케이션의 실시간 사용

외부 사용자를 대상으로 하는 애플리케이션에서 낮은 지연 시간이 중요한 사례입니다. 사용자 만족도를 유지하고 엄격한 성능 요구 사항을 충족하려면 시스템이 빠른 응답을 보장해야 합니다.

#### 1. 채팅 애플리케이션

**기업 활용 사례**: 전자상거래 플랫폼의 고객 지원 챗봇입니다. 사용자 만족도를 유지하고 문제를 실시간으로 해결하려면 빠른 응답이 중요합니다.

- **SLO**:
  - TTFT: 요청의 99%에서 ≤ 200ms
  - ITL: 요청의 99%에서 ≤ 50ms

#### 2. 검색 증강 생성(RAG)

**기업 활용 사례**: 재판 중 변호사를 위해 관련 판례를 실시간으로 검색하고 요약하는 법률 문서 검색 도구입니다.

- **SLO**:
  - 요청 지연 시간: 요청의 99%에서 ≤ 3s
  - TTFT: 요청의 99%에서 ≤ 300ms(생성되는 출력을 순차적으로 표시하는 경우)
  - ITL: 요청의 99%에서 ≤ 100ms(생성되는 출력을 순차적으로 표시하는 경우)

#### 3. 지시 수행 / 에이전트형 AI

**기업 활용 사례**: 회의 일정을 잡고 작업을 관리하는 가상 비서입니다. 사용자의 생산성을 높이려면 빠른 응답이 필수적입니다.

- **SLO**:
  - 요청 지연 시간: 요청의 99%에서 ≤ 5s

### 내부 업무의 실시간 사용

낮은 지연 시간이 중요하지만 외부 사용자 대상 애플리케이션보다는 요구 사항이 덜 엄격한 사례입니다. 일반적으로 기업 내부 팀에서 사용하는 시스템이지만, 서비스로 제공한다면 외부 사용자에게 성능을 보장해야 할 수도 있습니다.

#### 4. 콘텐츠 생성

**기업 활용 사례**: 광고 문구와 소셜 미디어 게시물을 생성하는 내부 마케팅 도구입니다. 외부 사용자 대상 애플리케이션보다 지연 시간이 조금 더 길어도 허용할 수 있습니다.

- **SLO**:
  - TTFT: 요청의 99%에서 ≤ 600ms
  - ITL: 요청의 99%에서 ≤ 200ms

#### 5. 코드 생성

**기업 활용 사례**: 엔지니어링 팀 내부에서 반복적인 기본 코드와 API 연동 코드를 생성하는 데 사용하는 개발자 생산성 도구입니다.

- **SLO**:
  - TTFT: 요청의 99%에서 ≤ 500ms
  - ITL: 요청의 99%에서 ≤ 150ms

#### 6. 코드 자동 완성

**기업 활용 사례**: 코드 조각을 자동으로 완성하여 개발자의 작업 효율을 높이는 통합 개발 환경(IDE) 플러그인입니다.

- **SLO**:
  - 요청 지연 시간: 요청의 99%에서 ≤ 2s

### 오프라인 배치 처리

처리량 극대화가 주된 목표인 사례입니다. 리소스 사용률과 비용 효율성을 최적화하기 위해, 주로 사용량이 적은 시간대에 대량의 데이터를 배치로 처리합니다.

#### 7. 요약

**기업 활용 사례**: 제품 개선에 필요한 정보를 얻기 위해 고객 리뷰를 요약하는 도구입니다. 야간에 대규모 배치로 처리합니다.

- **SLO**:
  - 처리량 극대화: 초당 요청 수 ≥ 100

#### 8. 분석

**기업 활용 사례**: 판매 데이터에서 실행 가능한 개선 방향을 도출하여 분기별 사업 전략 수립에 활용하는 데이터 분석 파이프라인입니다.

- **SLO**:
  - 처리량 극대화: 초당 요청 수 ≥ 150

## 목표 달성 여부 측정

위의 목표는 "요청의 99%에서 TTFT ≤ 200ms"처럼 임곗값과 요청 비율을 함께 지정합니다. GuideLLM은 두 요소를 모두 직접 측정합니다.

### 목표 선언

목표는 `--metrics`에 설정합니다. 각 목표는 밀리초 단위의 요청별 임곗값이며, 요청이 모든 목표를 충족해야 적합한 요청으로 판단합니다:

```bash
guidellm run \
  --backend kind=openai_http,target=http://localhost:8000 \
  --profile kind=concurrent,streams=32 \
  --data kind=synthetic_text,prompt_tokens=256,output_tokens=128 \
  --metrics '{"kind":"generative","slo":{"ttft_ms":200,"tpot_ms":50}}' \
  --constraint kind=max_duration,seconds=120
```

| 목표      | 비교 지표                    | 참고 사항                                                                                                                                                                                                                                                                                              |
| --------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ttft_ms` | 첫 토큰 생성까지 걸리는 시간 | 스트리밍 백엔드 필요                                                                                                                                                                                                                                                                                   |
| `tpot_ms` | 토큰 간 지연 시간            | 첫 토큰을 제외합니다. 첫 토큰을 포함하는 GuideLLM의 출력 토큰당 소요 시간과는 다릅니다. vLLM의 `tpot`과 가장 가까운 지표이지만 완전히 같지는 않습니다. vLLM은 요청이 완료될 때까지 측정하고, 토큰 간 지연 시간은 마지막 토큰을 받을 때까지 측정합니다. 토큰을 1개 이하로 생성하는 요청은 판정하지 않음 |
| `e2el_ms` | 요청 지연 시간               | 스트리밍 및 비스트리밍 백엔드 모두 지원                                                                                                                                                                                                                                                                |

이후 두 가지 지표를 보고합니다. SLO 달성률은 모든 목표를 충족한 요청의 비율이며, 요청 유효 처리량은 이러한 요청을 단위 시간당 처리한 수입니다. 오류가 발생한 요청은 목표 범위 안에 응답을 제공하지 못했으므로 목표를 충족하지 못한 요청으로 집계합니다. 실행 시간 제한에 도달하여 취소된 요청은 서버가 아니라 벤치마크 실행 종료로 중단된 것이므로 제외합니다. 비스트리밍 백엔드에 `ttft_ms`를 지정하는 경우처럼 워크로드에서 측정할 수 없는 지표를 목표로 지정하면 모든 요청이 판정 불가 상태로 남으며, 두 지표 모두 0이 아닌 미설정 상태로 보고됩니다.

### 목표를 충족하는 부하 찾기

목표를 선언하면 특정 부하 수준이 목표를 충족하는지 확인할 수 있습니다. `goodput` 프로파일은 목표를 충족하는 가장 높은 부하 수준을 탐색하며, 이는 용량 계획의 핵심 질문에 해당합니다.

```bash
guidellm run \
  --backend kind=openai_http,target=http://localhost:8000 \
  --profile kind=goodput,target_attainment=0.99 \
  --data kind=synthetic_text,prompt_tokens=256,output_tokens=128 \
  --metrics '{"kind":"generative","slo":{"ttft_ms":200,"tpot_ms":50}}' \
  --constraint kind=max_duration,seconds=120
```

`target_attainment`는 목표 중 "요청의 99%"에 해당하는 부분입니다. 탐색 과정에서는 목표를 충족하지 못하는 수준에 도달할 때까지 동시 요청 수를 두 배씩 늘립니다. 이후 목표를 충족하는 가장 높은 수준과 충족하지 못하는 가장 낮은 수준 사이에서 이분 탐색을 수행하며, 결과의 오차가 `tolerance`(기본값 10%) 이내가 되면 중단합니다.

탐색 중에는 요청률이 아닌 동시 요청 수를 조정합니다. 동시 요청 수를 고정하면 각 수준에서 정상 상태에 도달할 수 있습니다. 반면 서버가 지속적으로 처리할 수 있는 수준보다 요청률이 높으면 대기 요청이 끝없이 쌓이며, 이때의 측정값은 서버 자체의 성능보다 요청 적체 상태를 나타냅니다.

각 부하 수준은 유효 처리량이 아닌 달성률로 평가합니다. 달성률은 실제로 측정한 요청을 기준으로 계산하는 비율입니다. 따라서 측정 구간 중 첫 요청이 완료되기 전에 서버의 처리 파이프라인을 채우는 데 얼마나 많은 시간이 걸렸는지에 영향을 받지 않습니다.

### 결과 확인

포화 지점을 넘으면 요청률은 정체되지만 유효 처리량은 감소합니다. 요청 자체는 계속 완료되더라도 목표를 충족할 만큼 빠르게 완료되지는 않기 때문입니다. 다음은 이 저장소에 포함된 모의 서버에 동시 처리 슬롯 16개와 종단 간 지연 시간 목표 1500ms를 설정하여 측정한 결과입니다:

| 동시 요청 수 | 초당 요청 수 | 초당 유효 처리 요청 수 | 달성률 |
| ------------ | ------------ | ---------------------- | ------ |
| 16           | 24.6         | 24.6                   | 100.0% |
| 26           | 24.4         | 23.2                   | 95.1%  |
| 32           | 24.3         | 19.3                   | 79.6%  |

동시 요청 수가 16개와 32개일 때 요청률은 같으므로 처리량만 기준으로 탐색하면 두 경우를 구분할 수 없습니다. 동시 요청 수를 16개에서 32개로 늘리면 유효 처리량은 22% 감소합니다.

탐색 결과는 벤치마크 보고서의 `conclusions`에 추가됩니다. 각 탐색 실행의 달성률과 신뢰 구간, 목표를 충족하는 가장 높은 동시 요청 수와 충족하지 못하는 가장 낮은 동시 요청 수, 탐색을 중단한 이유가 포함됩니다.

각 탐색 실행의 달성률은 신뢰 구간을 기준으로 평가합니다. 신뢰 구간이 목표값의 양쪽에 걸쳐 있으면 실행 시간이 너무 짧아 목표 달성 여부를 판단할 수 없다는 뜻입니다. 이때 GuideLLM은 정밀해 보이는 수치를 보고하는 대신 경고를 표시합니다. 탐색 횟수 제한이나 스트림 수 상한에 도달하여 탐색을 중단한 경우에도 같은 경고를 표시합니다. 이때 보고되는 수준은 목표를 충족하는 최댓값이 아니라 하한이기 때문입니다. 테스트한 모든 수준이 목표를 충족하지 못했더라도 판단에 사용한 신뢰 구간이 목표값의 양쪽에 걸쳐 있으면, 목표를 달성할 수 없다는 결과 대신 판정 불가로 보고합니다. `--constraint kind=max_duration,seconds=...`의 시간을 늘리면 각 탐색 실행에서 더 많은 요청을 수집하여 신뢰 구간을 좁힐 수 있습니다.

과포화 시 강제 중단처럼 제약 조건으로 인해 실행 도중 중단된 탐색 결과는 기록되지만 탐색 경계로는 사용되지 않습니다. 이러한 실행에서는 진행 중인 요청을 취소하며, 취소된 요청은 달성률에서 제외됩니다. 따라서 서버가 실제로는 해당 동시 요청 수를 지속적으로 처리할 수 없더라도, 완료된 요청만 보면 목표를 충족한 것처럼 보일 수 있습니다.

## 결론

사용자 기대와 비즈니스 요구 사항을 충족하도록 LLM 배포 환경을 최적화하려면 적절한 SLO와 SLA를 설정해야 합니다. 지연 시간, 처리량 및 비용 효율성 사이에서 균형을 맞추면 운영 비용을 최소화하면서 높은 품질의 서비스를 제공할 수 있습니다. 위의 예제를 바탕으로 각 활용 사례에 맞는 SLO와 SLA를 정의하세요.
