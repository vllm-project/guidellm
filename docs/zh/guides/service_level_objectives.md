# 服务级别目标

服务级别目标（SLO）和服务级别协议（SLA）对于确保大语言模型（LLM）部署的质量和可靠性至关重要。它们定义了系统必须达到的、可衡量的性能与可靠性目标，以满足用户期望和业务需求。下文介绍 SLO/SLA 的关键概念、权衡因素，以及各种 LLM 使用场景的示例。

## 定义

### 服务级别目标（SLO）

SLO 是用于指导系统运行和优化的内部性能与可靠性目标。它们通常以可衡量的指标定义，例如延迟、吞吐量或错误率，并作为评估系统性能的基准。

### 服务级别协议（SLA）

SLA 是服务提供方与用户或客户之间的正式协议。协议会说明服务提供方承诺达到的性能和可靠性保证。如果未达到约定目标，SLA 通常还会规定相应的处罚或补偿。

## 延迟与吞吐量之间的权衡

为 LLM 部署设定 SLO 和 SLA 时，需要在延迟、吞吐量和成本效率之间取得平衡：

- **延迟**：处理单个请求所需的时间，包括首个 token 延迟（TTFT）和 token 间延迟（ITL）等指标。对于响应速度至关重要的面向用户应用，低延迟尤为重要。
- **吞吐量**：每秒处理的请求数。高吞吐量对于高效处理大规模工作负载至关重要。
- **成本效率**：单个请求的成本，取决于系统资源利用率和吞吐量。提升吞吐量通常有助于提高成本效率，但可能会增加单个请求的延迟。

例如，聊天应用可能优先考虑低延迟，以确保流畅的用户体验；而用于内容生成的批处理系统则可能优先考虑高吞吐量，以降低成本。

## 常见 LLM 使用场景的 SLO/SLA 示例

### 实时面向应用的使用场景

这类场景面向外部用户，低延迟至关重要。系统必须确保快速响应，以保持用户满意度并满足严格的性能要求。

#### 1. 聊天应用

**企业使用场景**：电商平台的客户支持聊天机器人。快速响应对于维持用户满意度并实时解决问题至关重要。

- **SLO**：
  - 99% 的请求 TTFT ≤ 200ms
  - 99% 的请求 ITL ≤ 50ms

#### 2. 检索增强生成（RAG）

**企业使用场景**：法律文档搜索工具，在法庭审理期间为律师实时检索并总结相关判例。

- **SLO**：
  - 99% 的请求延迟 ≤ 3s
  - 如果展示逐步生成的结果，99% 的请求 TTFT ≤ 300ms
  - 如果展示逐步生成的结果，99% 的请求 ITL ≤ 100ms

#### 3. 指令遵循 / 智能体 AI

**企业使用场景**：用于安排会议和管理任务的虚拟助手。快速响应对于提升用户工作效率至关重要。

- **SLO**：
  - 99% 的请求延迟 ≤ 5s

### 实时面向内部的使用场景

这类场景也重视低延迟，但要求通常不如面向外部用户的应用严格。系统一般供企业内部团队使用；如果作为服务提供，也可能需要面向外部用户的性能保证。

#### 4. 内容生成

**企业使用场景**：内部营销工具，用于生成广告文案和社交媒体帖子。与面向外部用户的应用相比，这类工具可以接受稍高的延迟。

- **SLO**：
  - 99% 的请求 TTFT ≤ 600ms
  - 99% 的请求 ITL ≤ 200ms

#### 5. 代码生成

**企业使用场景**：供工程团队内部使用的开发效率工具，用于生成样板代码和 API 集成代码。

- **SLO**：
  - 99% 的请求 TTFT ≤ 500ms
  - 99% 的请求 ITL ≤ 150ms

#### 6. 代码补全

**企业使用场景**：集成开发环境（IDE）插件，用于自动补全代码片段，提升开发效率。

- **SLO**：
  - 99% 的请求延迟 ≤ 2s

### 离线批处理场景

这类场景主要追求最大吞吐量。系统通常在非高峰时段批量处理大量数据，以优化资源利用率和成本效率。

#### 7. 摘要生成

**企业使用场景**：夜间批量处理客户评论并生成摘要，以提取产品改进所需的见解。

- **SLO**：
  - 最大化吞吐量：每秒至少 100 个请求

#### 8. 分析

**企业使用场景**：数据分析流水线，用于分析销售数据并生成可执行的见解，为季度业务战略提供依据。

- **SLO**：
  - 最大化吞吐量：每秒至少 150 个请求

## 根据这些目标进行测量

上述目标以“阈值 + 请求占比”的形式表达，例如“99% 的请求 TTFT ≤ 200ms”。GuideLLM 可以直接测量这两部分。

### 声明目标

通过 `--metrics` 设置目标。每项目标都是以毫秒为单位的单请求阈值；只有同时满足所有目标的请求才算符合要求：

```bash
guidellm run \
  --backend kind=openai_http,target=http://localhost:8000 \
  --profile kind=concurrent,streams=32 \
  --data kind=synthetic_text,prompt_tokens=256,output_tokens=128 \
  --metrics '{"kind":"generative","slo":{"ttft_ms":200,"tpot_ms":50}}' \
  --constraint kind=max_duration,seconds=120
```

| 目标      | 对应指标        | 说明                                                                                                                                                                                                                                                             |
| --------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ttft_ms` | 首个 token 延迟 | 需要使用流式后端                                                                                                                                                                                                                                                 |
| `tpot_ms` | token 间延迟    | 不包括首个 token。这与 GuideLLM 的“每个输出 token 耗时”（包含首个 token）不同。它与 vLLM 的 `tpot` 最接近，但并不完全相同：vLLM 测量到请求完成时的耗时，token 间延迟则测量到最后一个 token 被接收时的延迟。生成不超过一个 token 的请求不会被判定为符合或不符合。 |
| `e2el_ms` | 请求延迟        | 同时适用于流式和非流式后端                                                                                                                                                                                                                                       |

之后会报告两项指标：**SLO 达标率**，即满足所有目标的请求占比；以及**请求 goodput**，即符合目标的请求速率。出错的请求会计入达标率的分母，因为失败请求没有在目标范围内返回响应。运行达到时长限制时取消的请求则不计入，因为这些请求是由基准测试结束而取消的，并非服务器取消。若目标指定了工作负载无法测量的指标，例如对非流式后端设置 `ttft_ms`，所有请求都将处于无法判定状态，两项指标均显示为未设置，而不是 0。

### 查找目标所支持的负载

声明目标可以判断某个负载水平是否符合要求。`goodput` profile 会搜索符合目标的最高负载，这正是容量规划需要回答的问题。

```bash
guidellm run \
  --backend kind=openai_http,target=http://localhost:8000 \
  --profile kind=goodput,target_attainment=0.99 \
  --data kind=synthetic_text,prompt_tokens=256,output_tokens=128 \
  --metrics '{"kind":"generative","slo":{"ttft_ms":200,"tpot_ms":50}}' \
  --constraint kind=max_duration,seconds=120
```

`target_attainment` 表示目标中的“99% 的请求”部分。搜索会逐步将并发数翻倍，直到某个负载水平未达到目标；随后在最高达标水平与最低未达标水平之间进行二分搜索。当结果精度达到 `tolerance`（默认 10%）后，搜索即停止。

搜索调整的是并发数，而不是请求速率。每个并发水平都会进入稳定状态；如果请求速率超过服务器可持续处理的能力，积压就会无限增长，此时测得的是积压情况，而非服务器本身的性能。

每个负载水平依据达标率而非 goodput 进行评估。达标率是根据实际测量的请求计算出的比例，因此不受测量窗口内服务器在首个请求完成前需要多长时间填满处理流水线的影响。

### 解读结果

超过饱和点后，请求速率趋于平稳，而 goodput 会下降，因为请求虽然仍然完成，但完成速度已不足以达到目标。以下数据使用本仓库自带的模拟服务器测得，该服务器配置为 16 个并发槽位，端到端延迟目标为 1500ms：

| 并发数 | 每秒请求数 | 每秒 goodput | 达标率 |
| ------ | ---------- | ------------ | ------ |
| 16     | 24.6       | 24.6         | 100.0% |
| 26     | 24.4       | 23.2         | 95.1%  |
| 32     | 24.3       | 19.3         | 79.6%  |

并发数为 16 和 32 时，请求速率相同，因此只根据吞吐量驱动的搜索无法区分二者。两者之间的 goodput 下降了 22%。

搜索结束后会将结果附加到基准测试报告的 `conclusions` 中，包括每次探测的达标率和置信区间、最高达标和最低未达标的并发数，以及停止搜索的原因。

每次探测的达标率都会结合置信区间进行判断。如果置信区间跨越目标值，说明探测运行时间太短，无法作出判断；此时 GuideLLM 会发出警告，而不会报告看似精确的数字。如果搜索因探测预算或流数量上限而停止，也会发出相同警告，因为此时报告的负载只是下界，并非最高达标值。如果测试的每个负载水平都未达标，但用于判断的置信区间跨越了目标值，结果会标记为无法确定，而不会断言目标无法达到。提高 `--constraint kind=max_duration,seconds=...` 的时长，可以为每次探测收集更多请求并缩小置信区间。

如果某次探测在运行中被约束提前停止（例如强制执行的过饱和约束），该次结果会被记录，但不会用于确定搜索边界。这类运行会取消正在处理的请求，而这些请求不计入达标率，因此剩余已完成请求可能看起来符合目标，即使服务器实际上无法持续支持该并发水平。

## 总结

设置合适的 SLO 和 SLA 对优化 LLM 部署、满足用户期望和业务需求至关重要。通过平衡延迟、吞吐量和成本效率，组织可以在降低运营成本的同时提供高质量服务。本文中的示例可作为起点，帮助你根据具体使用场景制定 SLO 和 SLA。
