# 指标

GuideLLM 提供丰富的指标，用于评估和优化大语言模型（LLM）部署的性能。这些指标有助于了解模型在不同条件下的表现、识别瓶颈，并为扩展和资源分配做出明智决策。以下介绍 GuideLLM 测量的主要指标、定义、用途及其解读方式。

## 请求状态指标

### 成功、未完成和错误请求

- **成功请求**：已成功完成且未发生错误的请求数。
- **未完成请求**：已开始但尚未完成的请求数，通常由超时或中断导致。
- **错误请求**：因错误而失败的请求数，例如输入无效或服务器问题。

这些指标按状态细分整体请求情况，帮助了解 LLM 部署的可靠性和稳定性。

### 已发起请求

- **定义**：一次基准测试运行期间发起的请求总数，并按状态（成功、未完成、错误）细分。
- **用途**：帮助评估系统处理的工作负载，并了解成功请求与失败或未完成请求的比例。

## Token 指标

### 提示词 Token 数量与计数

- **定义**：发送给 LLM 的输入提示词中的 token 数量。
- **用途**：帮助了解输入数据的复杂度及其对模型性能的影响。

### 输出 Token 数量与计数

- **定义**：LLM 根据输入提示词生成的 token 数量。
- **用途**：帮助评估模型的输出长度，以及输出长度与延迟和资源使用量之间的关系。

## 性能指标

### 请求速率（每秒请求数）

- **定义**：每秒处理的请求数。
- **用途**：反映系统的吞吐量和处理并发工作负载的能力。

### 请求并发数

- **定义**：同时处理的请求数。
- **用途**：帮助评估系统处理并行工作负载的能力。

### SLO 达成率

- **定义**：满足所有已配置延迟目标的请求比例。仅当通过 `--metrics` 设置了目标时才会报告。出错的请求视为不符合目标。在运行时长限制到达时被取消的请求，以及无法评估目标的请求（例如，非流式后端无法评估首个 token 的生成时间），都不会计入分子或分母。
- **用途**：直接说明部署是否达到某个目标，例如“99% 的请求首 token 延迟低于 200 毫秒”。由于它是比例而非速率，因此不会随测量时段的长短而变化。

### 请求有效吞吐量

- **定义**：每秒完成的、符合目标的请求数。已完成但未达到目标的请求会计入请求速率，但不会计入有效吞吐量，因此有效吞吐量始终不高于请求速率。
- **用途**：区分有效容量和原始容量。超过服务器饱和点后，请求速率可能保持平稳，而有效吞吐量会下降，因为请求虽然仍能完成，但完成速度已不足以满足使用要求。

### 每秒输出 Token 数

- **定义**：以吞吐量衡量时，所有请求平均每秒生成的输出 token 数。
- **用途**：帮助了解服务器生成输出 token 的性能和效率。

### 每秒总 Token 数

- **定义**：以吞吐量衡量时，所有请求平均每秒处理的提示词 token 与输出 token 总数。
- **用途**：帮助了解服务器处理提示词和输出 token 的整体性能和效率。

### 请求延迟

- **定义**：处理单个请求所需的时间，即从开始到完成的耗时。
- **用途**：这是评估系统响应能力的重要指标。

### 生成延迟

- **定义**：`generation_delay` 是调度器开始从 `requests_generator` 生成下一个会话，到创建该会话的请求信息之间所花费的时间。它在调度器状态中按会话记录一次，而不是按单个请求记录。
- **用途**：显示负载生成器为每个会话准备并入队所花费的时间（包括遍历数据集和协调器准备）。延迟接近零表示请求生成跟得上；延迟较大则表示数据集处理或入队路径成为瓶颈，与后端延迟和派发调度无关。

### 派发延迟

- **定义**：`request_dispatch_delay` 是 `request_start - targeted_start`，即请求计划到达时间与实际发送时间之间的间隔。
- **用途**：显示基准测试本身是否跟得上配置的到达计划。并发上限已满时，请求无法派发；这段等待时间不计入请求延迟。延迟接近零表示报告的延迟涵盖了完整情况；延迟较大则表示负载生成器落后，服务器实际收到的请求速率低于设定值。派发延迟本身不能说明请求为何迟到；前序轮次延迟和轮次调度延迟会分别拆分这段等待时间。

### 前序轮次延迟

- **定义**：`turn_predecessor_delay` 是派发延迟中因前一个轮次在本请求计划开始时间之后仍在运行而产生的等待时间。如果请求没有前序轮次，或前序轮次在计划时间之前已完成，则该值为零。如果两种情况都发生，从计划时间起等待前序轮次完成的时间计为前序轮次延迟，之后的等待时间计为轮次调度延迟。两者之和等于派发延迟。
- **用途**：显示是前一个轮次而非负载生成器导致该请求未能按时开始。

### 轮次调度延迟

- **定义**：`turn_scheduling_delay` 是派发延迟减去前序轮次延迟。它表示请求已到计划时间且不再受前序轮次阻塞后所经历的等待时间，包括反序列化轨迹、排队和工作线程周转所花费的时间。如果思考时间（`requeue_delay`）超过计划时间，也会计入此项。轨迹回放不会设置思考时间。
- **用途**：可用于判断 GuideLLM 是否跟不上，或运行基准测试的机器配置是否不足。

### 计划延迟

- **定义**：`request_scheduled_latency` 是 `request_end - targeted_start`，即从计划到达时间而非实际派发时间开始计算的请求延迟。三个时间戳都存在时，它等于派发延迟加请求延迟。
- **用途**：描述遵循配置到达计划的客户端会经历的情况，包括等待派发的时间。基准测试跟得上时，该值与请求延迟相同；基准测试落后时，两者之间的差值就是请求延迟单独无法体现的延迟。

派发延迟、前序轮次延迟、轮次调度延迟和计划延迟仅适用于部分调度策略。请参阅下文的[派发延迟和计划延迟的适用范围](#applicability-of-dispatch-delay-and-scheduled-latency)。在相对轨迹回放中，`targeted_start` 会随前一个轮次移动，因此这些延迟是相对于移动后的目标时间测量的，而不是相对于原始轨迹时钟。

### 首 token 延迟（TTFT）

- **定义**：生成首个输出 token 所花费的时间。
- **用途**：表示模型的初始响应时间，这对面向用户的应用至关重要。

### Token 间延迟（ITL）

- **定义**：生成输出中连续 token 之间的平均时间，不包括首个 token。
- **用途**：用于评估 token 生成是否流畅、速度是否稳定。

### 每个输出 Token 的耗时

- **定义**：生成每个输出 token 所花费的平均时间，包括首个 token。
- **用途**：详细展示模型生成 token 的效率。

### 最后一次往返时间

- **定义**：对于实时 WebSocket 后端（`openai_websocket`），从最后一个已发送数据包到收到最后一个 token 的时间。
- **用途**：衡量流式交互的尾延迟（即最后一段输出比最后一段输入晚到多久）。

### 平均往返时间（Avg RTT）

- **定义**：对于 WebSocket 后端，收到的 token 时间戳的平均值减去已发送数据包时间戳的平均值。
- **用途**：估算一次请求中发送到接收的平均延迟。该值是近似值，因为它假设已发送的数据包与收到的 token 在时间上均匀对应。

## 测量窗口、预热与冷却

基准测试配置档可以设置 `warmup` 和 `cooldown` 时段，将活动测量窗口夹在两者之间。预热期间发送的请求仍会完整执行，但报告中的指标仅统计 `measure_start`（预热结束）到 `measure_end`（冷却开始）之间的数据。

并非所有指标都以相同方式应用这个窗口：

- **请求级指标**：请求总数、请求延迟、并发数、每个请求的 token 数量等，会计入生命周期与测量窗口有重叠的请求，即使请求在预热期间开始，或在冷却期间结束。
- **事件级指标**：TTFT、首个输出 token 耗时（TTFOT）、Token 间延迟（ITL）和每 token 吞吐率，只会计入时间戳落在窗口内的事件。因此，请求可能计入请求总数，但其部分或全部 token 事件会被排除。

对于 token 延迟，GuideLLM 会根据事件发生时间进行筛选，而不是检查整个请求的时间跨度：

- **TTFT**：如果从请求开始到首个 token 到达之间的时间段与测量窗口部分重叠，就会计入该样本。在预热期间开始、但在预热结束后才输出首个 token 的请求会贡献一个 TTFT 样本；如果首个 token 在 `measure_start` 之前到达，则不会计入，即使请求在活动测量阶段才完成。
- **TTFOT**：使用首个 *内容* token 的时间戳（`first_output_token_iteration`）。如果推理 token 或工具 token 先于可见输出，TTFOT 可能与 TTFT 不同。
- **ITL**：如果从首个 token 到请求完成之间的时间段与窗口部分重叠，就会计入。

预热旨在让系统在测量前达到稳定状态。事件级筛选也能避免预热前的 token 时间影响延迟和吞吐量统计，同时仍会统计跨越窗口边界的长时间运行请求。

## 统计摘要

GuideLLM 使用 `StatusDistributionSummary` 和 `DistributionSummary` 模型，为上述每项指标提供详细的统计摘要，包括以下统计量：

### 摘要统计量

- **平均值（Mean）**：指标数值的平均值。
- **中位数（Median）**：指标数值排序后的中间值。
- **众数（Mode）**：指标中出现次数最多的数值。
- **方差（Variance）**：衡量指标数值的变化程度。
- **标准差（Standard Deviation，Std Dev）**：方差的平方根，用于表示数值的离散程度。
- **最小值（Min）**：指标的最小数值。
- **最大值（Max）**：指标的最大数值。
- **计数（Count）**：该指标的数据点总数。
- **总和（Total Sum）**：该指标所有数值的总和。

### 百分位数

GuideLLM 会为每项指标计算一组完整的百分位数，包括：

- **第 0.1 百分位数（p001）**：有 0.1% 的数据低于该数值。
- **第 1 百分位数（p01）**：有 1% 的数据低于该数值。
- **第 5 百分位数（p05）**：有 5% 的数据低于该数值。
- **第 10 百分位数（p10）**：有 10% 的数据低于该数值。
- **第 25 百分位数（p25）**：有 25% 的数据低于该数值。
- **第 75 百分位数（p75）**：有 75% 的数据低于该数值。
- **第 90 百分位数（p90）**：有 90% 的数据低于该数值。
- **第 95 百分位数（p95）**：有 95% 的数据低于该数值。
- **第 99 百分位数（p99）**：有 99% 的数据低于该数值。
- **第 99.9 百分位数（p999）**：有 99.9% 的数据低于该数值。

### 置信区间

以上每个统计摘要都是根据有限数量的请求估算得出的。GuideLLM 会在报告数值的同时，说明测量结果的精确程度。

- **`mean_ci`**：平均值的双侧置信区间。
- **`percentile_cis`**：每个已报告百分位数的置信区间；如果本次运行时间太短，无法计算区间，则为 `null`。

使用 `--metrics kind=generative,confidence=0.95` 设置置信水平。默认值为 0.95；设为 `null` 时，报告指标但不提供置信区间。每次基准测试的置信水平会记录在 `config.confidence` 中。

控制台会同时显示平均值和区间的半宽，例如 `80.5 ± 3.9`；如果样本不足以界定某个百分位数，控制台会在该百分位数旁标记 `*`。对于包含区间的指标，CSV 会追加 `Mean CI` 和 `Percentile CIs` 列。后者按百分位数记录区间，并附带置信水平。这些列会放在每行末尾，因此现有列的位置不会改变。

#### 哪些指标会报告置信区间

只有每个请求恰好记录一次、且每个数值都是一个观测值的指标才会报告置信区间，包括请求延迟、TTFT、首个输出 token 耗时、往返时间指标、token 数量、流式迭代次数、派发延迟和计划延迟。

以下两组指标不报告置信区间：

- **Token 间延迟和每个输出 Token 的耗时。** 这两项指标的平均值按输出 token 数量加权，因此计算的是总生成时间与 token 总数之比，而不是对可互换观测值求平均。请注意，它们的 `count` 表示累加后的 token 数量，不是请求数。
- **速率分布**，例如每秒请求数和每秒输出 token 数。这些指标根据事件时间计算得出，而不是来自逐请求观测值。

#### 为什么可能没有百分位数置信区间

报告的百分位数是顺序统计量：`p99` 是排序后样本中排名为 `ceil(0.99n)` 的数值。双侧区间需要该排名两侧都有观测值，因此至少需要 `ceil(log(alpha / 2) / log(q))` 个请求。在默认置信水平 0.95 下，p95 需要 72 个请求，p99 需要 368 个请求，p999 需要 3688 个请求。

样本数低于这些门槛时，区间会报告为 `null`。请注意：成功请求少于 100 个时，报告的 `p99` 就是本次运行中最慢的请求；少于 1000 个时，`p999` 也是如此。

#### 置信区间的含义与局限

置信区间描述的是本次运行在自身条件下测量结果的精确程度，并将其中的请求视为独立观测值。它不能说明再次运行相同基准测试时，数值会有多大变化。如果连续请求共享某种在不同运行之间会变化的条件，例如生成期间服务器的负载，这两种变化就会有所不同。因此，要比较不同运行的结果，需要进行多次运行，不能只看单次运行的置信区间。

### 统计摘要的用途

- **平均值和中位数**：表示指标数值的集中趋势。
- **方差和标准差**：表示指标的变异程度和一致性。
- **最小值和最大值**：显示指标数值的范围。
- **百分位数**：展示数值分布，帮助识别离群值，以及不同服务水平下的性能。

结合这些指标和统计摘要，GuideLLM 可以帮助用户深入了解 LLM 部署情况、优化性能，并确保可扩展性和成本效益。

## 派发延迟和计划延迟的适用范围 {#applicability-of-dispatch-delay-and-scheduled-latency}

派发延迟（Dispatch Delay）、前序轮次延迟（Turn Predecessor Delay）、轮次调度延迟（Turn Scheduling Delay）和计划延迟（Scheduled Latency）都根据 `targeted_start` 计算，因此只有定义了到达时间计划的策略才能用这些指标描述相对于计划的延迟：

- `constant` 和 `poisson` 根据配置的速率计算每个目标时间。
- `trace` 根据重放数据集中的时间戳计算每个目标时间。没有相对时间戳的 trace 请求会回退到基准测试开始时间，并受到下文所述 `throughput` 策略的限制。

`synchronous`、`concurrent` 和 `throughput` 策略会改用 ASAP 式目标时间，但这些目标各自有不同的问题：

- 除了按配置的 rampup 分批发出的请求，`synchronous` 和 `concurrent` 会将前一个请求完成的时间作为目标时间。因此，目标时间取决于系统自身的响应，以此为基准计算延迟会形成循环：它描述的是测试框架的周转时间，而不是相对于到达计划的延迟。
- `throughput` 会将每个请求的目标时间都设为基准测试开始时间，因此该数值会随运行时间增长，并不是真正的延迟。

对于这三种策略，**这些指标会报告为 `null`**，而不是零，并且不会出现在 CSV 列中。报告为零会被理解为“未测得延迟”，这比“不适用”表达了更强、也更容易误导的结论。这一点对默认的 `sweep` 配置档很重要，因为它会在基于速率的策略之外，同时运行 `synchronous` 和 `throughput`。

对于多轮对话数据集，轮次的目标时间会在调度器时隙开启时确定，而不是等前一轮完成后再确定。因此，轮次之间配置的思考时间会计入派发延迟和轮次调度延迟。

适用时，这些指标会记录在序列化报告和 CSV 输出中，供离线分析。无论何种情况，它们都不会出现在最终的控制台延迟表中，因为该表会在一次运行中的所有配置档间共用。
