# 文档翻译

GuideLLM 在权威的英文文档之外，还发布少量由社区维护的简体中文页面。这一翻译试点有意限制了范围，以便项目在扩大范围之前评估维护和审查成本。

## 政策

- `docs/en/` 下的英文文档是权威来源，但从仓库根目录的 `CODE_OF_CONDUCT.md`、`CONTRIBUTING.md` 和 `DEVELOPING.md` 生成的开发者页面除外。
- 简体中文页面位于 `docs/zh/` 下，其路径与英文页面对应。
- 英文文档的更改不要求同步更新翻译，也不会因翻译滞后而受到阻碍。
- 如果翻译页面落后于英文源文件，页面会显示警告并链接至最新的英文页面。
- CLI 输出、日志、错误消息、文档字符串和生成的 API 参考页面不在翻译范围内。
- 机器翻译可以辅助贡献者，但仍由懂中文的审查者负责把关语义和语言质量。

## 源文件跟踪

每个翻译页面都在页面的 YAML front matter 中以 `source_sha256` 记录其英文源文件的 SHA-256 摘要。请写成 `source_sha256: !!str "<digest>"`，以便外观类似数字的哈希值仍被视为字符串，并让 Markdown 格式化工具保留引号。中文和韩文页面的路径与其英文源文件对应：`docs/zh/<path>.md` 和 `docs/ko/<path>.md` 对应 `docs/en/<path>.md`。三个生成的开发者页面则跟踪仓库根目录中的源文件。

运行 CI 使用的非阻塞式验证：

```bash
uv run python docs/scripts/check_translations.py
```

该命令同时检查中文和韩文翻译，并将过时页面报告为警告。结构问题、缺失页面以及围栏代码示例发生更改都会被报告为错误。添加 `--strict` 可将过时的翻译视为错误；添加 `--language zh` 或 `--language ko` 可只检查一种语言。

将翻译与最新英文页面对照审查后，只更新该页面记录的源文件版本：

```bash
uv run python docs/scripts/check_translations.py --update docs/zh/getting-started/install.md
```

将翻译页面 front matter 中更新后的 `source_sha256` 与翻译内容一同提交。

## 导航行为

文档钩子根据每个页面的源路由选择导航。对于 `docs/zh/` 下的页面，导航会尽可能使用已翻译的页面；尚未翻译的条目则链接到英文页面，并标注 `(English)`。这些英文页面使用常规英文侧边栏，因此读者返回 `docs/zh/` 下的页面时，导航会恢复为中文。语言选择按页面生效，在进入回退的英文页面后不会被记住。

只有已知的章节标题会被翻译。API 文档插件将 API 导航章节命名为 `API Reference`；`reference/` 是其生成的路由，而非章节标题。生成的 API 参考页面本身仍为英文。

## 审查职责

英文审查者可以审查站点集成、技术内容、命令、链接、代码示例以及权威站点的回归问题。懂中文的审查者检查语义准确性、术语和语言质量。审查者无需掌握两种语言，也能承担其中一部分职责。

翻译 pull request 应包含：

- 权威英文页面及其源文件版本；
- 关于术语或技术决策的简短英文说明；
- 确认命令、标识符和围栏代码示例均已保留；
- 严格翻译检查和常规文档检查的输出。

AI 生成的草稿和回译可作为审查辅助，但本身不能作为批准的依据。

## 术语

保留产品名称、命令名称、CLI 标志、配置键、指标缩写、代码标识符和代码示例。在有助于提高准确性的情况下，首次使用时优先给出中文术语，并在其后附上约定俗成的英文术语或缩写，例如“首 token 延迟（TTFT）”。

在可行的情况下，术语更改应在同一个 pull request 中一致地应用于现有中文页面。
